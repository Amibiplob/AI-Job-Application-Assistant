# Isolated Paddle sandbox staging preparation

Prepared from `a79cfd6`. This is an undeployed, self-hosted staging profile, not evidence of a genuine Paddle purchase. Read [the webhook design](paddle-webhook-processing.md) for the inbox, lease fencing and entitlement transaction design.

## Isolation boundary and authorization

Use a **separate host and PostgreSQL cluster**, never a production cluster with a different database name. The website and scheduled workers must share that staging host's protected Unix socket. Vercel is deliberately unsupported by this profile: [Vercel Cron Jobs run only on production deployments](https://vercel.com/docs/cron-jobs/quickstart), whereas sandbox billing rejects production deployments. Do not change that rejection to accommodate a cron. No public worker route, external queue, live Paddle host or automatic migration was added.

`PADDLE_STAGING_PROFILE=isolated` requires `DEPLOYMENT_ENV=staging`, `BILLING_DEPLOYMENT_ENV=sandbox`, a valid provisioned UUID identity, HTTPS origin, and a separate `PADDLE_SANDBOX_DATABASE_URL`. `DATABASE_URL` must be empty. Only an explicit Unix socket `/tmp/<single-directory>`, database `paddle_sandbox_*`, and runtime role `paddle_staging_*` are accepted; TCP, passwords, arbitrary connection options and duplicate parameters are rejected. Production/Vercel variables and live-looking Paddle credentials fail closed. Enabling sandbox website traffic without the isolated profile also fails closed, rather than reusing the normal database.

On **every application and ingress pool checkout**, the server verifies the database name, role, provisioner-owned identity marker, and cluster inventory. The role cannot be superuser, create roles/databases, bypass RLS, have memberships, own the database/marker/schema, or mutate the marker. Another connectable non-template database other than the administrative `postgres` database rejects the cluster. Missing markers fail before application SQL. These checks depend on honest operator provisioning; copying a staging marker onto a production cluster is forbidden.

Worker authorization is local OS authorization, not a reusable HTTP secret: a dedicated service UID, private configuration file owned by that UID with **exact mode 0600**, and a protected PostgreSQL socket with peer authentication. The launcher rejects symlinks, repository configuration files, extra arguments, unapproved settings and oversized files. It constructs a fresh environment; inherited app, PostgreSQL and Node options cannot select the database or enable features in child processes. Parent directories, code, Node executable and service units must be provisioner-owned and not writable by the runtime UID. Anyone controlling that UID or the host can run its workers; do not share the UID with other services.

## Scheduling, bounds and monitoring

| Operation | Schedule | Bounds |
| --- | --- | --- |
| webhook inbox | 30 seconds after previous completion | Default five jobs; max ten; each canonical reconciliation 25s, lease 60s, five attempts with durable backoff. |
| periodic account reconciliation | 5 minutes after previous completion | Default five accounts; max ten; a fresh 25s provider deadline per account, 3s per HTTP request; three attempts before operator recovery. |
| inbox cleanup | hourly | At most 100 eligible rows per transaction; locked rows skipped. |
| health | every minute | Aggregate counts only; SQL 5s / query 6s / checkout 3s deadlines. |

The private launcher bounds worker child execution at 180s (TERM, KILL after 10s). Units additionally use GNU timeout 180s, TimeoutStartSec 195s and KillMode=control-group to terminate descendants. Website is a separate long-running unit. PostgreSQL transaction rollback plus expiring leases handles termination; a completed event receipt and entitlement transition commit together, and expired tokens cannot commit. HTTP requests share each account's deadline; deadline checking before billing mutation prevents completion after an expired canonical read. No grace period or quota reset was introduced. Free remains 3 and eligible Pro 100 successful matches per UTC month.

Worker journals contain fixed operation/result strings, numeric counts and durations; cleanup logs counts only. No payload, event/customer/subscription/user IDs, database URL, provider body, exception stack or secrets are emitted by these operational entry points. Restrict journal access and enforce rotation/retention. Existing website/infrastructure logs also require operator review before deployment. Health emits retained, failed, outstanding, oldest pending age, exhausted account count, overdue reconciliation age and healthy boolean. Exit 1 alerts at retained >=8,000 (hard inbox cap 10,000), any failed/exhausted work, pending age >=180s or reconciliation overdue >=600s.

**Deployment prerequisite:** configure real external monitoring for failed oneshots, abnormal duration, missing timer runs/heartbeats, website/webhook 4xx/5xx, PostgreSQL capacity and backup success. Health alone cannot detect that health itself stopped, an empty queue with a stopped timer, or a silently dead host. Verify alerts reach an operator with a deliberately failed disposable preflight and paused timer. No alert delivery integration or successful delivery is claimed. Never log request Authorization or Paddle-Signature headers in proxies.

## Inbox retention and recovery

Retain completed `done` inbox metadata for 30 days. Delete at most 100 per cleanup run only when an independent `billing_events(provider='paddle_sandbox',event_id)` receipt exists. **Retain that minimal receipt ledger indefinitely** to preserve deduplication after inbox cleanup. Concurrent cleanup uses SKIP LOCKED and cannot touch account/entitlement/usage tables. Replay after cleanup is processed as an already-recorded event; provider state cannot be granted twice.

Pending/processing/failed/ignored inbox rows are never automatically deleted. Failed/ignored rows require reviewed triage; ignored delivery floods consume the same finite cap and must alert before it is reached. Do not automate retry resets or delete failures to silence alerts. Stop workers before manual repair; review the verified stored reference and canonical provider state, then follow the lease-safe recovery procedure in the webhook document. Never rewrite ownership hints, event fingerprints or processed receipts. Backups share access controls and have a separately approved retention/deletion policy; account deletion retains only minimal receipts as already designed. A backup restore requires pausing ingestion/workers and reconciling authoritative provider state before resuming.
